# FaidATech localization data

FaidATech has 15 language placements across three tiers and 13 unique locale codes. English (`en`), French (`fr`), Spanish (`es`), Arabic (`ar`), and Simplified Chinese (`zh-CN`) are Global. Swahili (`sw`), Amharic (`am`), Hausa (`ha`), Yoruba (`yo`), and Afaan Oromoo (`om`) are African. Amharic, Afaan Oromoo, Tigrigna (`ti`), Somali (`so`), and Sidama (`sid`) are Ethiopian. Amharic and Afaan Oromoo intentionally appear in both African and Ethiopian tiers but each has one catalog.

Each `catalogs/<locale>.json` file has `meta` and `messages` objects. `meta.code` is the locale code; `meta.direction` is `ltr` or `rtl`; `meta.sourceLocale` is `en`; `meta.tierMemberships` lists every tier placement; `meta.translationStatus` records `source`, `machine_draft`, or `fallback_required`; and `meta.reviewStatus` records `source`, `machine_draft`, `fallback_required`, or `native_reviewed`. English is authoritative. French, Spanish, Arabic, Simplified Chinese, Swahili, and Hausa have machine-generated draft messages. Amharic, Yoruba, Afaan Oromoo, Tigrigna, Somali, and Sidama currently point to English content with `fallback_required` metadata. No non-English locale has native-reviewed status. AI-generated content is not certified error-free; a qualified native-language reviewer must approve it before FaidATech can claim native accuracy.

Message IDs are stable dotted keys. Keep strings as plain text. Interpolation uses named placeholders such as `{count}` and `{destination}`; every locale must retain the exact source placeholder set. Run `node scripts/validate-i18n.mjs` after changing catalogs to check the exact locale set, key parity, tier and direction metadata, non-empty strings, fallback provenance, and interpolation tokens. A `fallback_required` catalog must exactly match the English source until a reviewed translation replaces it.

The locale provider uses the explicitly saved selection, then the browser language, then English. Missing locale messages and unknown browser preferences safely fall back to English. When a locale is `fallback_required`, the provider returns English source strings and sets the document language to `en` so assistive technology does not misidentify English as the requested language. Direction still follows the selected locale; Arabic uses right-to-left layout. The selector displays an English status notice for machine drafts and fallback-required locales. Selection is saved in browser local storage; the application does not transmit locale preferences to a third party.

Dynamic QR payloads may contain optional `localizedContent`, keyed by any supported locale code. Each locale entry can override `title`, `description`, `summary`, `body`, `buttonLabel`, or `displayName`, and can contain a string map of `fields`. Use stable field paths such as `vcard.jobTitle`, `menu.categories[0].name`, `menu.categories[0].items[0].description`, and `tourism.historicalMedia[0].caption`. Values are validated plain text, never rendered as HTML. Visitors select the requested locale, then receive field-level fallback from `localizedContent.en`, then the destination's existing base payload. Selecting a UI language does not machine-translate customer content.

Tourism `audioLinks` and `transcripts` support all 13 unique locale codes. The four historical property names (`amharic`, `afaanOromoo`, `english`, `tigrigna`) remain accepted and normalize to `am`, `om`, `en`, and `ti` when read, preserving saved QR records.
